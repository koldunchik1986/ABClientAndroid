# Дополнение для app2 / ANClient

Этот файл является самостоятельным `AGENTS` для отдельного Android-модуля `app2/` (`ANClient`). Уточнения этого раздела имеют приоритет при работе именно с `app2/`.

1. **Область изменений для ANClient.**
   * Для задач по `app2/` все изменения выполняются только в `app2/` и связанных с ним корневых файлах сборки (`settings.gradle`, `gradlew2.bat`, `AGENTS2.MD`).
   * Основной модуль `app/` не трогать, если задача явно относится к `ANClient/app2`.
   * Папка `ABClient/` по-прежнему только для чтения и используется только как эталон ПК-версии.

2. **Правило именования при портировании в app2.**
   * Все runtime-имена, ресурсы, файлы, URL-параметры, JS-маркеры, CSS-классы и лог-префиксы, которые в исходном Android-коде использовали `AB`/`ABC`/`ABCLIENT`, в `app2` должны быть приведены к `AN`/`ANC`/`ANCLIENT`.
   * Все Java/Kotlin package/import/module-ссылки в `app2` должны использовать `ru.neverlands.anclient`, а не package основного Android-модуля.
   * Если в унаследованном тексте ниже встречается пример импорта из основного Android-модуля, для `app2` читать и применять его как импорт из `ru.neverlands.anclient`.
   * Базовые соответствия:
     * `AB` -> `AN`
     * `ABC` -> `ANC`
     * `ABCLIENT` -> `ANCLIENT`
     * `ABClient` -> `ANClient` только если это runtime-имя Android-клиента, а не ссылка на ПК-версию.
   * Уже приведенные runtime-сущности в `app2` должны сохранять ANC/AN-вид: `AncCell`, `ancells.xml`, `anfavorites.xml`, `anteleports.xml`, `anthings.xml`, `ancache`, `anmove`, `ancell`, `an_*` параметры, `an-room-*`, `an_autoboi_*`, `ANCLIENT_*`.
   * Новые файлы и новые портированные участки в `app2` не должны возвращать старые runtime-префиксы `AB`/`ABC`/`ABCLIENT`.

3. **Комментарии и ссылки на ПК-версию.**
   * Комментарии, Javadoc и описания в `TODO2` могут и должны сохранять ссылки на ПК-версию `ABClient`, если речь идет об исходном C# эталоне.
   * Такие комментарии не считаются ошибкой и не переименовываются в `ANClient`, чтобы не терять связь с источником портирования.
   * Если строка является runtime-идентификатором, логом, именем файла, ресурсом, схемой URL или параметром запроса, она должна быть `AN/ANC`, а не `AB/ABC`.

4. **Документация, анализ и задачи для app2.**
   * Все markdown-файлы анализа, портирования, задач и отладки для `app2/ANClient` создавать и обновлять только в `TODO2/`.
   * Папку анализа основного Android-модуля не использовать для новых задач `app2`; старые планы основного модуля не смешивать с `TODO2/`.
   * Если для `app2` нужен файл вида `todo_*.md`, `todo_task_*.md`, `todo_DebugApp.md` или `Debug/debug_log_*.md`, он должен находиться в `TODO2/`.

5. **Проверка перед сдачей app2.**
   * Сборка: `./gradlew2.bat --no-daemon` или `./gradlew.bat --no-daemon :app2:assembleDebug`.
   * Проверить, что в `app2/src/main` нет runtime-вхождений package основного Android-модуля, `ABCLIENT`, `abclient`, `abcells.xml`, `abcache`, `AbcCell`, `ABC_VISITED`, `abmove`, `abcell`, `ab_*` для новых ANClient-контуров.
   * Допустимы только комментарии, где `ABClient` явно означает ПК-версию или C# источник.
   * Проверить UTF-8 без BOM и отсутствие mojibake.

# Работа с кодовой базой: Основные правила

0.  **Обязательное чтение правил перед каждым ответом и изменением кода.**
    *   Перед любым анализом, правкой, запуском сборки и перед формированием ответа обязательно перечитывать:
        *   `.cursor/rules/AI.txt`
        *   `.cursor/rules/general rule.txt`
        *   `.cursor/rules/UTF8.ps1`
        *   `AGENTS.MD`
        *   `AGENTS2.MD` при работе с `app2/ANClient`
    *   Это обязательный pre-check для всех задач без исключений.
    *   При конфликте инструкций приоритет: System/Developer/User → `AGENTS2.MD` для `app2/ANClient` → `AGENTS.MD` → остальные локальные правила.

1.  **Кодировка (UTF-8 без BOM) и анти-mojibake.**
    *   Все файлы (`.java`, `.kt`, `.xml`, `.md`, `.gradle`, `.properties`, `.json`, `.js`, `.cs`) только в **UTF-8 без BOM**.
    *   **Запрещено:** Windows-1251, CP1251, любая legacy-кодировка.
    *   **Mojibake признак:** кракозябра вида `РЎР...`, `РџС...`, `Ð...`, `Ñ...`, `???` вместо кириллицы. Если видна — восстановить текст в UTF-8 перед любыми функциональными изменениями.
    *   **Перед сдачей:** grep в диффе на mojibake-паттерны, убедиться что все кириллица читаемая.

2.  **Папка `ABClient` — только для чтения.**
    *   `ABClient/` содержит исходный C# код ПК-версии — это эталон для портирования.
    *   **ЗАПРЕЩЕНО:** вносить изменения в файлы папки ABClient.
    *   **ВСЕ изменения для ANClient:** только в `app2/` и связанных с ним корневых файлах сборки.
    *   Используем ABClient как справочник по архитектуре и логике, но реализуем в Android-модуле `app2/`.

3.  **Функционал портируется, не удаляется.**
    *   Ключевые системы ПК-версии (прокси, автоматизация, система боя и т.д.) должны работать в Android.
    *   **Запрещено:** полное удаление функционала. Если нельзя реализовать как есть — создать fallback.
    *   **Диагностика:** комментирование/отключение допустимо ТОЛЬКО для поиска проблемы. Финальное решение должно содержать работающий аналог.

4.  **User-Agent только браузерный (анти-детект).**
    *   Сервер не должен видеть признаков неофициального клиента в HTTP-заголовках.
    *   **ЗАПРЕЩЕНО:** `ABClient`, `ANClient`, `Android; ABClient`, `Android; ANClient`, любые кастомные метки в User-Agent.
    *   **ОБЯЗАТЕЛЬНО:** только браузерные User-Agent (Chrome/Firefox style), согласованные по проекту.
    *   **Проверка перед коммитом:** `grep -r "User-Agent\|ABClient\|ANClient\|Android;" app2/` на предмет идентификаторов клиента в сетевых заголовках.

5.  **Стабильность ручных HTML-кликов (приоритет > фоновые процессы).**
    *   **Суть:** Ручной клик по HTML-кнопке (например, `Взять из казны`, `main.php?get_id=60`) должен ВСЕГДА сработать с первого раза.
    *   **Принцип:** Ручное действие пользователя в WebView имеет абсолютный приоритет над фоновыми автозапросами. Нельзя отправлять конкурирующие запросы одновременно с ручным action.
    *   **Защита от регрессии (обязательно):**
        1. **Foreground-режим:** Если нет признаков боя, `AutoModeForegroundService` НЕ должен стартовать auto-turn probe (он может перехватить ручной клик).
        2. **Guard ручного контекста:** В `MainActivity` сохраняется флаг, что открыт non-fight HTML-контекст. Если true — серверный auto-probe для автохода/автобоя подавляется до завершения ручного действия.
        3. **Suppression window:** После ручного клика устанавливается короткое окно (100-500ms) подавления фоновых probe-вызовов, чтобы избежать гонки запросов.
    *   **Инварианты JS-фиксов (сохранять при любом рефакторинге):**
        *   В `HtmlUtils.getJsFix()` ВСЕГДА оставлять заглушки DOM-элементов: `transfer`, `complect`, `hbar` (если страница их ожидает).
        *   Удаление/изменение БЕЗ замены = ошибка `Cannot read properties of null (reading 'innerHTML')` и падение HTML-обработки.
        *   **Правило:** не плодить дублирующие обходы. При поломке → исправляем существующий guard/тайминг/ветку, не добавляем новый параллельный контур.
    *   **Чек-лист перед сдачей:**
        *   ✅ HTML-действия выполняются с первого клика.
        *   ✅ В логах нет серии конфликтных `an_bg_probe`/auto-turn вызовов одновременно с ручным кликом.
        *   ✅ Нет `null.innerHTML` ошибок на страницах с JS-инъекциями.
        *   ✅ В боях: автопроцессы работают корректно (не деградация поведения).

6.  **Управление VCode через SessionManager (для ВСЕХ новых функций с защитой).**
    *   **Что это:** `SessionManager` — единая система управления кодом защиты (VCode). Парсит VCode из каждого HTML ответа сервера и автоматически валидирует перед использованием в AJAX.
    *   **КРИТИЧНЫЕ правила:**
        1. **ЗАПРЕЩЕНО** сохранять `AppVars.VCode` как глобальный буфер → потеря VCode при смене контекста/PHPSESSID.
        2. **ОБЯЗАТЕЛЬНО** использовать: `SessionManager.getInstance().getValidVCodeForAction("action_name")` вместо `AppVars.VCode`.
        3. **ОБЯЗАТЕЛЬНО** добавить импорт: `import ru.neverlands.anclient.utils.SessionManager;`
        4. **ОБЯЗАТЕЛЬНО** обработать null-результат: если `getValidVCodeForAction()` вернула `null`, добавить fallback (reload main.php или skip действия).
    *   **Когда вносить миграцию на SessionManager:**
        *   Новые AJAX-запросы (рыбалка, бой, навигация, быстрые действия).
        *   Исправление ошибки "Неверный код защиты" в любом модуле.
        *   Рефакторинг существующих функций с `AppVars.VCode`.
    *   **Проверка перед коммитом:**
        *   grep по коду: `grep -r "AppVars\.VCode" app2/src/main/java/` — не должно быть **новых** вхождений (только в SessionManager).
        *   Логи проверяют на наличие: `✅ VCODE_PARSED` (успех), `⚠️ SessionManager: vcode not available` (ошибка + fallback).
    *   **Архитектурные детали:**
        *   SessionManager парсит VCode из каждого HTML ответа через WebViewRequestInterceptor.
        *   SessionContext — неизменяемый контейнер с версионированием (tracking VCode source).
        *   Thread-safe доступ через ReentrantReadWriteLock для параллельных потоков.

7.  **Модульная архитектура — выделение логики в специализированные Handler'ы.**
    *   **Суть:** Сложная функциональность (проверки, обработка событий, сложные условия) должна быть в отдельных модулях, не в ViewModel/Manager. Это предотвращает размазывание логики и улучшает читаемость, тестируемость, переиспользуемость.
    *   **Архитектурное разделение:**
        1. **Manager'ы и ViewModel'и** — только koordinация (decision points), не реализация.
        2. **Handler'ы** — реализуют конкретную задачу (цепочка проверок, обработка, retry).
        3. **Один Handler** — одна область (FightAnnounceHandler для проверок перед боем, FastActionCleanupHandler для очистки и т.д.).
        4. **Callback pattern** — Handler передаёт результат callback'ом (Manager/ViewModel решают, что вызвать next).
    *   **КОГДА вынести в Handler:**
        *   >3 каскадных условий (если → проверь то → проверь это → потом то → retry).
        *   Повторяющаяся логика в нескольких файлах (пример: VCode-проверки в разных местах).
        *   Специализированная задача одной области (прокси-проверки, guard-валидация, state-очистка).
        *   Переиспользуемость в других экранах/потоках/сценариях.
    *   **Структура Handler'а — шаблон:**
        ```java
        public class [Специализация]Handler {
            public static void on[Event](
                [ContextData] context,
                [CheckData] checkData,
                Runnable onApprovedCallback,
                Runnable onRejectedCallback) {
                // Каскадирующие проверки с early-return
                // Логирование каждой точки решения
                // Retry-логика для временных сбоев
                // Вызов callback при успехе/отказе
            }
        }
        ```
    *   **Примеры Handler'ов:**
        *   `FightAnnounceHandler` — проверки перед боем: captcha → guard → VCode, retry при fail, callback при approve.
        *   `FastActionCleanupHandler` — очистка fast-action: проверка FastNeed, затирание, логирование.
        *   `HtmlButtonClickValidator` — валидация ручных кликов до отправки.
    *   **Логирование в Handler'ах — ОБЯЗАТЕЛЬНО:**
        *   Каждое решение: проверка выполнена, выполнена с fail, запланирован retry — логируется.
        *   Используется: `Log.i()` + `FileLogger.trace()` (двойное логирование).
        *   Формат: `[HANDLER_NAME_EVENT]` пример: `[FIGHT_ANNOUNCE_REJECTED: captcha visible]`.
        *   Префиксы: `✅ APPROVED`, `❌ REJECTED`, `⏳ RETRY`, `⚠️ WARNING`.
    *   **Проверка перед сдачей:**
        *   ✅ ViewModel/Manager'е вызовы к Handler'ам только координация, без логики.
        *   ✅ ВСЕ проверки находятся в Handler'е, не разбросаны.
        *   ✅ Handler логирует каждое решение с понятным префиксом.
        *   ✅ Новая функция с >3 условий? Сначала спросить: создать Handler?

8.  **Переиспользование существующих фиксов (anti «fix-на-fix») — обязательно перед любой реализацией.**
    *   **Суть:** Перед добавлением нового кода всегда проверить, есть ли в проекте уже существующая реализация/фикс (возможно под похожим именем функции, константы, параметра, запроса, guard-ветки, retry-ветки, таймера).
    *   **Обязательный pre-check перед правками:**
        1. Поиск по проекту по ключам: имя функции/константы/параметра, URL/endpoint, текст сообщения, лог-префикс.
        2. Найти текущую точку принятия решения (decision point) и исправлять **её**, а не создавать параллельный контур.
        3. Если есть 2+ похожих ветки — сначала объединить/упростить существующую реализацию, затем править поведение.
    *   **Запрещено:**
        *   Добавлять дублирующий «временный» фикс рядом с существующим, если можно безопасно исправить текущую ветку.
        *   Создавать новые флаги/константы/таймеры, если аналог уже существует и покрывает задачу.
    *   **Разрешено добавить новый модуль/Handler только если:**
        *   Нет эквивалентной точки расширения в текущем коде;
        *   Логика действительно новая и не укладывается в существующий контур без ухудшения читаемости.
    *   **Проверка перед сдачей (чек-лист):**
        *   ✅ В описании изменений указано, какой существующий контур найден и почему правка внесена именно туда.
        *   ✅ Нет новых дублирующих веток для той же задачи.
        *   ✅ Устаревшие обходы удалены/слиты, если они больше не нужны.
        *   ✅ Логирование не дублирует одинаковые события в нескольких параллельных точках.

# Анализ папки для app2

Когда поступает задача проанализировать целую папку для портирования или доработки `app2/ANClient`, необходимо создать сводный markdown-файл в `TODO2/` для отслеживания прогресса **анализа** каждого файла в этой папке. Для отслеживания общего прогресса **реализации** используется сводный файл верхнего уровня в `TODO2/` (например, `todo_ANClient.md`).

### Статус-маркеры

*   `[ ]` - **Не проанализирован**: Детальный анализ файла еще не проводился.
*   `[x]` - **Проанализирован**: Детальный анализ файла (`todo_filename.md`) в `TODO2/` завершен.
*   `[-]` - **Отложен**: Анализ или реализация отложены.
*   `[+]` - **Реализован/Портирован**: Весь функционал, описанный в файле или папке, полностью реализован в `app2/ANClient`.

### Шаг 1: Создание сводного файла анализа папки (`todo_FolderName.md`)

1.  **Расположение:** `TODO2\todo_FolderName.md`.
2.  **Назначение:** Отслеживать **статус анализа** каждого файла внутри папки `FolderName`.
3.  **Структура:**

    ```markdown
    # Анализ папки [FolderName]

    ## Список файлов и статус анализа

    | Файл             | Описание                               | Статус подробного анализа |
    | ---------------- | -------------------------------------- | -------------------------
    | `[FileName1.cs]` | [Краткое описание]                     | `[ ]` Не проанализирован      
    | `[FileName2.cs]` | [Краткое описание]                     | `[x]` Проанализирован         
    ```

### Шаг 2: Обновление сводного файла проекта (`todo_ProjectName.md`)

1.  **Расположение:** `TODO2\todo_ProjectName.md` (например, `TODO2\todo_ANClient.md`).
2.  **Назначение:** Отслеживать общий **статус реализации (портирования)** для каждой папки именно в `app2/ANClient`.
3.  **Процесс:**
    *   Когда **все** задачи по портированию функционала из папки `FolderName` выполнены (то есть, все ее файлы не просто проанализированы, а их функционал реализован в `app2/ANClient`), статус этой папки в файле `todo_ProjectName.md` меняется на `[+]`.

    ```markdown
    # Анализ портирования ANClient

    ## Список подпапок и статус реализации

    | Папка     | Описание                               | Статус реализации |
    | --------- | -------------------------------------- | -----------------
    | `Forms`   | Основные формы и диалоги.              | `[+]` Реализована     
    | `Helpers` | Вспомогательные классы.                | `[ ]` Не реализована  
    ```


### Шаг 3: Процесс работы

1.  **Первичное сканирование и проверка:**
    *   Получите список **всех файлов** (включая `.cs`, `.xml`, `.js`, `.resx` и т.д.) в анализируемой папке (например, `ABClient\PostFilter`).
    *   Получите список всех `.md` файлов в соответствующей папке с анализами (например, `TODO2\todo_ANClient\todo_PostFilter`).
    *   В сводном файле `todo_PostFilter.md` создайте таблицу и изначально пометьте все файлы статусом `[ ] Не проанализирован`, если для них еще не создан детальный `.md` файл.
    *   **Проверьте соответствие существующих `.md` файлов:** Одновременно просмотрите соответствующую папку с анализами (`TODO2\todo_ANClient\todo_PostFilter`). Если в ней есть файлы `todo_*.md`, убедитесь, что они действительно описывают файлы из папки `ABClient\PostFilter` или соответствующий порт в `app2/`. Если найден несоответствующий файл, сообщите об этом.
    *   **Сравните количество и состав файлов:** Убедитесь, что для каждого файла в исходной папке существует соответствующий `todo_filename.filetype.md` файл в папке анализа.
    *   **При расхождении:** Если обнаружено, что для какого-либо файла отсутствует `.md` файл, необходимо немедленно создать его, проведя подробный анализ этого файла и занеся результаты в новый `.md` файл согласно общим инструкциям.
    *   **Проверьте соответствие существующих `.md` файлов:** Если в папке анализа есть файлы `todo_*.md`, убедитесь, что они действительно описывают существующие файлы в исходной папке. Если найден несоответствующий `.md` файл (описывающий удаленный или переименованный исходный файл), сообщите об этом.
    *   Для каждого файла в исходной папке постарайтесь дать краткое описание его назначения в сводном файле `todo_FolderName.md`.

3.  **Обновление сводного файла:**

# Инструкция по созданию подробного анализа для портирования

## Основные правила

1.  **Подробный анализ:** При выполнении портирования кода с ПК версии (C#) на `app2/ANClient` (Java/Kotlin) необходимо сначала провести подробный анализ исходного файла. Результаты анализа должны быть записаны в файл `TODO2\ProjectName\todo_filename.cs.md` на русском языке.
2.  **Соблюдение названий:** Обязательно соблюдать названия переменных, функций и констант из ПК версии в Android версии для сохранения преемственности и облегчения отладки.
3.  **Ведение списка задач:** Всегда вести подробный список задач в файле `TODO2\todo_task_timestamp.md` на русском языке и обновлять его по мере выполнения.

## Процесс портирования

### Шаг 1: Анализ и документирование

1.  **Анализ исходного C# файла:**
    *   **Задача:** Полностью понять, что делает класс, его методы, с какими данными и UI он работает в оригинальном приложении.
    *   Это первый и самый важный шаг в `todo_filename.cs.md`.

2.  **Проверка на существующую реализацию в app2:**
    *   **Когда:** *После* того, как вы полностью поняли функциональность C# кода.
    *   **Как:** Искать в `app2/` по ключевым словам, названиям классов, уникальным строкам.
    *   **Результат:** Этот шаг определяет дальнейший план. Либо мы портируем с нуля, либо дорабатываем существующий код.

3.  **Написание плана портирования:**
    *   На основе результатов предыдущих двух шагов составляется детальный план действий для `app2/ANClient`.
    *   **Промпт для анализа:** Перед созданием кода портированного приложения необходимо проанализировать текущий код `app2/` на наличие уже присутствующих элементов. Если их нет, то уже реализовывать подробно.

**Фраза-триггер:** "*Обязательно производить сначала запись анализа и подробных описаний и инструкций в TODO2\todo_filename.filetype.md на руссокм языке, а после уже приступать к написанию кода...*"

**Расшифровка:**

После того как вы убедились, что функциональность не реализована, приступайте к анализу и документированию:

1.  **Полностью проанализировать исходный файл** из ПК-версии (например, `MyClass.cs`).
2.  **Создать markdown-файл** в папке `TODO2` с именем, соответствующим исходному файлу (например, `TODO2\todo_MyClass.cs.md`).
3.  **Заполнить этот файл подробной информацией** на русском языке, включая:
    *   **Назначение файла:** Что делает этот класс/компонент в оригинальном приложении.
    *   **Анализ UI (если применимо):** Описание всех элементов интерфейса, их состояний и событий.
    *   **Анализ логики:** Описание ключевых методов, алгоритмов, используемых переменных и констант.
    *   **Взаимодействие:** Как этот компонент связан с другими частями приложения.
    *   **План портирования:** Конкретные шаги по переносу функциональности на Android, включая выбор подходящих Android-компонентов и архитектурных решений.

### Шаг 2: Написание кода и отслеживание прогресса

**Фраза-триггер:** *"...а после уже приступать к написанию кода с подробным описанием и подробнными сносками используя названия функций, переменных и констант и приблизительной архитектуры и названия папок, в как в ПК версии (из которой мы портируем)"*

**Расшифровка:**

После того как файл анализа создан и утвержден, можно приступать к написанию кода, соблюдая следующие принципы:

1.  **Преемственность названий:**
    *   **Переменные:** `userName` в C# должен стать `userName` в Java/Kotlin.
    *   **Функции/Методы:** `CalculateTotal()` в C# должен стать `calculateTotal()` в Java/Kotlin (с поправкой на конвенцию именования).
    *   **Константы:** `MAX_USERS` в C# должен стать `MAX_USERS` в Java/Kotlin.
2.  **Архитектурное соответствие:**
    *   **Структура папок:** Если в ПК-версии есть папка `Helpers` или `Utils`, следует создать аналогичную структуру в Android-проекте (например, `helpers` или `utils` в соответствующем пакете).
    *   **Архитектурные паттерны:** Если в оригинальном коде используется определенный паттерн (например, Singleton, Factory), следует по возможности воспроизвести его в портированной версии, адаптируя под особенности Android.
3.  **Подробное описание кода:**
    *   При написании кода оставлять комментарии, объясняющие сложные или неочевидные моменты, особенно если реализация на Android сильно отличается от оригинала.
    *   В описании коммитов или в отчетах о проделанной работе давать подробные сноски и объяснения, почему были приняты те или иные решения.

**Отслеживание статуса задач:**

В процессе выполнения задач, описанных в `TODO2/todo_*.md` файлах, необходимо маркировать их статус. Используйте следующие обозначения:

*   `[x]` - **Выполнено**
*   `[ ]` - **Не выполнено**
*   `[-]` - **Отложено** (если выполнение задачи по какой-то причине блокируется или переносится)

**Пример:**

```markdown
### План реализации

- [x] Создать layout-файл `activity_profile.xml`
- [x] Создать класс `ProfileActivity.java`
- [ ] Реализовать логику сохранения данных
- [-] Реализовать функцию `DetectProxy()` (отложено до реализации сетевого модуля)
```

## Структура файла анализа (`TODO2/todo_filename.cs.md`)

Файл анализа должен содержать следующие разделы:

### 1. План портирования [ИмяФайла].cs

Краткое описание назначения исходного файла. Например: `Файл AutoLogon.cs реализует диалоговое окно с обратным отсчетом перед автоматическим входом в игру.`

### 2. Функциональность в C#

Подробное описание того, как реализована функциональность в исходном C# коде.

*   **Назначение:** Какую задачу выполняет данный компонент?
*   **UI:** Какие элементы пользовательского интерфейса используются и как они выглядят?
*   **Логика:** Как работает основная логика? Какие классы, методы и события используются? Как обрабатываются пользовательские взаимодействия?
*   **Данные:** Как и где хранятся данные, связанные с этим компонентом?

**Пример для `AutoLogon.cs`:**

*   **Назначение**: Дать пользователю несколько секунд, чтобы отменить автоматический вход в игру. Если пользователь ничего не делает, вход происходит автоматически.
*   **UI**: Окно отображает имя пользователя, для которого выполняется вход, и две кнопки: "Отмена" и кнопка подтверждения (например, "Войти (10)").
*   **Обратный отсчет**: При открытии окна запускается `System.Windows.Forms.Timer`. Каждую секунду он уменьшает счетчик и обновляет текст на кнопке подтверждения, показывая оставшееся время.
*   **Авто-подтверждение**: Когда счетчик доходит до нуля, форма автоматически закрывается с результатом `DialogResult.OK`, что инициирует вход в игру.
*   **Отмена**: Пользователь может нажать кнопку "Отмена", чтобы прервать таймер и отменить автологин.

### 3. Решение для портирования на Android

Описание того, как данная функциональность будет реализована на Android. Какие классы и подходы будут использоваться?

**Пример для `AutoLogon.cs`:**

Эта функциональность легко реализуется с помощью стандартного `AlertDialog` и системного класса `android.os.CountDownTimer`.

### 4. План реализации

Пошаговый план реализации на Android.

1.  **Создание UI:** Описание того, как будет создан пользовательский интерфейс (XML-разметка или программно).
2.  **Реализация логики:** Подробное описание того, как будет реализована логика, включая создание методов, обработчиков событий и т.д.
3.  **Взаимодействие с другими компонентами:** Как новый компонент будет взаимодействовать с другими частями приложения.

**Пример для `AutoLogon.cs`:**

1.  **Создать утилитный метод** для показа диалога, который будет принимать `Context`, имя пользователя и `callback` для обработки результата.
    ```java
    public interface AutoLogonCallback {
        void onLoginConfirmed();
        void onLoginCancelled();
    }

    public static void showAutoLogonDialog(Context context, String userName, AutoLogonCallback callback) { ... }
    ```

2.  **Реализация `showAutoLogonDialog`**:
    *   Создать `AlertDialog.Builder` с заголовком "Автоматический вход" и сообщением, включающим `userName`.
    *   Установить кнопки:
        ```java
        builder.setNegativeButton("Отмена", (dialog, which) -> {
            // Таймер будет остановлен в обработчике onCancel
        });
        builder.setPositiveButton("Войти", (dialog, which) -> {
            // Этот обработчик сработает при нажатии или по окончании таймера
            callback.onLoginConfirmed();
        });
        ```
    *   Создать и показать диалог: `AlertDialog dialog = builder.create(); dialog.show();`

3.  **Настройка `CountDownTimer`**:
    *   После `dialog.show()`, получить ссылку на кнопку подтверждения: `final Button positiveButton = dialog.getButton(AlertDialog.BUTTON_POSITIVE);`
    *   Создать и запустить `CountDownTimer`:
        ```java
        final CountDownTimer timer = new CountDownTimer(10000, 1000) { // 10 секунд
            @Override
            public void onTick(long millisUntilFinished) {
                positiveButton.setText("Войти (" + (millisUntilFinished / 1000) + ")");
            }

            @Override
            public void onFinish() {
                if (dialog.isShowing()) {
                    dialog.dismiss();
                    callback.onLoginConfirmed();
                }
            }
        }.start();
        ```

4.  **Обработка отмены**:
    *   Добавить слушатель отмены/закрытия диалога, в котором будет останавливаться таймер, чтобы избежать утечек и лишних срабатываний.
        ```java
        dialog.setOnCancelListener(dialogInterface -> {
            timer.cancel();
            callback.onLoginCancelled();
        });
        ```
        Обработчик `setNegativeButton` также вызовет `OnCancelListener`.

# Комплексная отладка (Debug)

При возникновении сложных, многоуровневых или взаимосвязанных проблем, которые затрагивают несколько модулей или требуют глубокого анализа, необходимо придерживаться следующего процесса:

1.  **Создание основного файла отладки:** Первым шагом является создание файла `TODO2/todo_DebugApp.md` (или с другим соответствующим названием).
2.  **Назначение файла:** Этот файл становится центральным местом для:
    *   Полного и подробного описания всех наблюдаемых проблем.
    *   Декомпозиции комплексной проблемы на отдельные, более мелкие подзадачи.
    *   Формулирования гипотез о причинах каждой подзадачи.
    *   Составления пошагового плана для диагностики и решения каждой подзадачи.
    *   Отслеживания прогресса с помощью стандартных статус-маркеров (`[ ]`, `[x]`, `[-]`).
3.  **Системный подход:** Решение проблем должно происходить поэтапно, в соответствии с планом, изложенным в `TODO2/todo_DebugApp.md`.

# Отладка и Логирование

Для отладки сложных проблем, связанных с сетевым взаимодействием и обработкой данных, в проекте реализована система детального логирования.

-   **Расположение логов:** Детальные debug-логи, создаваемые классом `DebugLogger`, сохраняются в папку `Logs` **в корне проекта**.
-   **Именование файлов:** `Log_{timestamp}.txt` (например, `Log_20250927_111808.txt`).
-   **Получение логов:** Эти файлы создаются приложением в его внутренней директории. Для анализа их необходимо вручную извлечь с устройства и поместить в папку `Logs` в корне проекта.

# Журналирование действий при отладке

В дополнение к основному файлу отладки (`TODO2/todo_DebugApp.md`), для каждой сессии отладки `app2/ANClient` может создаваться отдельный файл журнала в папке `TODO2/Debug/`.

1.  **Именование файла:** `debug_log_{timestamp}.md` (например, `debug_log_20250929_123000.md`).
2.  **Назначение:** Этот файл служит для ведения хронологического, неизменяемого журнала **всех действий**, предпринятых в ходе отладки. В отличие от `todo_DebugApp.md`, который содержит высокоуровневый план и статус, этот файл фиксирует сам пошаговый процесс поиска и решения проблемы.
3.  **Содержимое:** В файл последовательно записываются:
    *   **Действие:** Какая команда была выполнена (`read_file`, `run_shell_command`, `replace` и т.д.).
    *   **Обоснование:** Краткое объяснение, почему это действие было необходимо в данный момент.
    *   **Результат:** Краткий итог выполнения (например, "Файл прочитан", "Сборка успешна", "Обнаружена ошибка X в логах").
    *   **Выводы:** Какие умозаключения сделаны на основе полученного результата и какой следующий шаг.

Это позволяет не "заменять проделанные работы" в основном файле, а иметь полную историю анализа и исправлений для последующего разбора. Основной файл `TODO2/todo_DebugApp.md` при этом продолжает использоваться для общего плана и отслеживания статуса верхнеуровневых задач.

6.  **Обязательное файловое логирование критичных цепочек (дополнительно к logcat).**
    *   **Правило:** Любые правки в критичных runtime-цепочках (чат/polling, авто-бой, авто-босс, авто-клад, fast-action, навигация, прокси/HTTP-interceptor) должны сопровождаться записью в файловый лог через `FileLogger`/`LogcatFileRecorder`, а не только через `Log.d/e`.
    *   **Требование:** Диагностические события из критичных цепочек должны быть доступны в `files/Logs/...` даже при переполнении системного буфера logcat.
    *   **Сегментация logcat:** для режима полной записи logcat использовать 10-минутные сегменты файлов (включается настройкой в UI).
    *   **UI-инвариант:** переключатель в `Настройки -> Разработка` (`record_logcat_to_file`) должен управлять записью logcat текущего процесса в `files/Logs/Logcat`.
    *   **Антирегрессия:** при рефакторинге нельзя удалять существующее файловое логирование критичных цепочек без эквивалентной замены.

7.  **Управление FastNeed при быстрых действиях (очистка обязательна).**
    *   **Суть:** `FastActionManager.fastStart()` устанавливает `AppVars.FastNeed = true`, блокируя авто-рыбалку/авто-питьё. После fast-action'а ОБЯЗАТЕЛЬНО затирать FastNeed.
    *   **Критичное правило:** **После завершения любого fast-action вызвать `FastActionManager.fastCancel("reason")`**, даже если action асинхронный или через таймер.
    *   **Правильный порядок:**
        1. Проверить `AppVars.FastNeed == true`
        2. Вызвать `fastCancel("action_finished")` с понятной причиной
        3. Логировать через FileLogger перед затиранием
    *   **Типичные баги:**

9.  **Порядок вызовов при инициализации боя (markFightInProgress ПЕРЕД LezFight).**

        *   В `FightAuto.java` — главный парсер боевых страниц
        *   В любых новых местах, где создаётся LezFight

10. **VCode кэширование и инвалидация в разных контекстах (актуально по SessionManager).**
    *   **Суть:** единый источник VCode — `SessionManager`. Он хранит `currentContext` (последний распарсенный VCode) и отдельный боевой fallback-кэш (`fightStartVCode`), чтобы не терять код защиты в бою.
    *   **Как сейчас реально работает TTL (важно):**
        1. **Дефолт для всех действий** через `getValidVCodeForAction(actionName)` = **300_000 ms (5 минут)**.
        2. **Спец-режим только для `actionName="fight_fallback"`** = **120_000 ms** (`FIGHT_CONTEXT_TIMEOUT`).
        3. При `fightInProgress=true` и наличии `fightStartVCode` SessionManager может вернуть боевой кэш, даже если `currentContext` пустой или устарел.
        4. Fast-action НЕ имеет отдельного TTL внутри SessionManager: используется общий контракт (дефолт 5 минут), если не передан кастомный `maxAgeMs`.
    *   **Обязательные правила использования:**
        1. **Запрещено** читать/писать `AppVars.VCode` в новом коде.
        2. Перед любым защищённым запросом брать код только через `SessionManager.getInstance().getValidVCodeForAction("action_name")`.
        3. Если для конкретного действия нужен более жёсткий TTL — использовать перегрузку `getValidVCodeForAction("action_name", maxAgeMs)`.
        4. Каждое новое место парсинга HTML, где потенциально есть vcode, должно вызывать `parseVCodeFromHtml(html, source)`.
        5. Для боевых страниц при наличии `fight_pm[4]` использовать `cacheFightVCode(vcode, "fight")` (не ждать только асинхронный парсинг).
    *   **Инвалидация и очистка (по текущей логике кода):**
        1. `onInvalidProtectionCodeError(failingVCode, actionName)` очищает `currentContext`, если failing-код совпал с текущим.
        2. `invalidateContext(reason)` — принудительная очистка `currentContext`.
        3. `clearFightContext()` очищает только боевое состояние (`fightInProgress`, `fightStartTimeMs`, `fightStartVCode`) и возвращает обычный режим TTL; `currentContext` этим методом не обнуляется.
        4. При явной смене сессии/логауте нужно вызывать **оба** шага: `invalidateContext(...)` + `clearFightContext()`.
    *   **Fallback при `null` от SessionManager (обязательно в каждом месте вызова):**
        *   Перезагрузить/обновить страницу контекста (`main.php` или профильный frame),
        *   либо отложить действие до следующего цикла,
        *   и обязательно залогировать причину пропуска (`NO_SESSION` / `STALE_SESSION` / `EMPTY_VCODE`).
    *   **Чек-лист перед сдачей:**
        *   ✅ Нет новых обращений к `AppVars.VCode` вне SessionManager.
        *   ✅ В каждом защищённом действии обработан `null` от `getValidVCodeForAction(...)`.
        *   ✅ Для боевого сценария есть корректные вызовы `markFightInProgress()` и `clearFightContext()`.
        *   ✅ Логи содержат маркеры `VCODE_PARSED`, `VALID_VCODE`, `NO_SESSION`/`STALE_SESSION` и, при бое, `FIGHT_CACHE`.

12. **Единый модуль логирования — AppLog (обязательно для ВСЕХ прикладных модулей).**
    *   **Что это:** `AppLog` — фасад двойного логирования: каждый вызов (`d/i/w/e`) пишет в **logcat** + дублирует в **FileLogger** (файлы `files/Logs/Critical/`). Это обеспечивает сохранность критичных логов даже при переполнении системного буфера logcat.
    *   **КРИТИЧНЫЕ правила:**
        1. **ЗАПРЕЩЕНО** использовать прямой `android.util.Log.*` в прикладных модулях (все, кроме `AppLog.java`, `FileLogger.java`, `LogcatFileRecorder.java`).
        2. **ЗАПРЕЩЕНО** использовать shorthand `Log.d/i/w/e` (импорт `android.util.Log`) в прикладных модулях.
        3. **ОБЯЗАТЕЛЬНО** использовать: `AppLog.d(tag, message)`, `AppLog.i(tag, message)`, `AppLog.w(tag, message)`, `AppLog.e(tag, message)` и перегрузки с `chain` и `Throwable`.
        4. **ОБЯЗАТЕЛЬНО** добавить импорт: `import ru.neverlands.anclient.utils.AppLog;`
        5. **ЗАПРЕЩЕНО** оставлять `import android.util.Log;` в прикладных модулях — только в инфраструктурных (`AppLog`, `FileLogger`, `LogcatFileRecorder`).
    *   **API AppLog (справочно):**
        *   `AppLog.d(tag, msg)` / `AppLog.d(chain, tag, msg)` — debug
        *   `AppLog.i(tag, msg)` / `AppLog.i(chain, tag, msg)` — info
        *   `AppLog.w(tag, msg)` / `AppLog.w(chain, tag, msg)` / `AppLog.w(tag, msg, error)` / `AppLog.w(chain, tag, msg, error)` — warning
        *   `AppLog.e(tag, msg)` / `AppLog.e(chain, tag, msg)` / `AppLog.e(tag, msg, error)` / `AppLog.e(chain, tag, msg, error)` — error
        *   `AppLog.getStackTraceString(error)` — аналог `Log.getStackTraceString`
    *   **Инфраструктурные модули (ИСКЛЮЧЕНИЯ — могут использовать `android.util.Log` напрямую):**
        *   `AppLog.java` — сама обёртка, делегирует в `android.util.Log` + `FileLogger`
        *   `FileLogger.java` — файловый логгер, использует `Log.getStackTraceString` и `Log.e/w/d` для металогирования своих ошибок
        *   `LogcatFileRecorder.java` — рекордер logcat, использует `Log` для металогирования
    *   **Когда использовать параметр `chain`:**
        *   Если лог относится к конкретной критичной цепочке (автобой, авторыбалка, прокси, VCode) — передавать chain для группировки в отдельный файл лога: `AppLog.d("AUTO_FISH_TRACE", TAG, msg)`.
        *   Если лог общий — использовать 2-arg вариант: `AppLog.d(TAG, msg)`.
    *   **Проверка перед коммитом:**
        *   grep по коду: `grep -r "android\.util\.Log\." app2/src/main/java/` — не должно быть вхождений вне `utils/AppLog.java`, `utils/FileLogger.java`, `utils/LogcatFileRecorder.java`.
        *   grep по коду: `grep -r "import android\.util\.Log;" app2/src/main/java/` — не должно быть вхождений вне тех же трёх файлов.
        *   grep по shorthand: `grep -rn "^\s*Log\.[diwe](" app2/src/main/java/` — не должно быть вхождений.
