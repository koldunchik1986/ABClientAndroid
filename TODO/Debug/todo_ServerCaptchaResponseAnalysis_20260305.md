# Разбор ответов сервера по завершению боя и капче (2026-03-05)

## Цель
Отделить:
- баг клиентской обработки завершения боя;
- штатное серверное требование капчи.

## Наблюдения по `Logs/logcat_runtime_20260305_02.txt`

1. Клиент фиксирует завершение боя:
   - `mainPhpFight: FIGHT ENDED with autoboi ON - processing finish`
2. При этом в цикле отсутствует рабочий `FightLink`:
   - `mainPhpFight: FightLink missing ...`
3. Запросов `get_id=61&act=7` в проблемном фрагменте нет.
4. Сервер повторно отдает fight-frame со state:
   - `fight_ty = [1,300,50,0,6,...,"2","720865496",...,4]`
5. Из-за fallback-перезагрузки `main.php` цикл повторяется.

## Что это значит

- `fight_ty[4]=6` в этих кадрах не дает готовый `FightLink` через текущий parser.
- Это клиентская дыра в обработке завершающей формы (`FEND`) при пустом `FightLink`.
- Капча и ее отсутствие — отдельная серверная ветка, не тождественная этому циклу.

## Что сделано в коде

1. Добавлен fallback-разбор server-side формы завершения (`FEND`) в `MainPhp`:
   - метод `buildFightEndFormSubmitHtml(...)`.
2. Если `code` обязателен, но пустой/`????`, автосабмит не делается.
3. Если форма корректна и капча не нужна, выполняется автосабмит `FEND`.
4. Убран зацикливающий fallback-редирект на `main.php` при пустом `FightLink`.

## Вывод по "обходу капчи"

- Способ обхода капчи не реализован.
- Реализована только корректная обработка сценария "без капчи" (автоклик/автосабмит завершения).
- Если сервер требует `code`, остается штатный поток ручного ввода.

## Практический критерий проверки фикса

- В новом runtime-логе после конца боя:
  - не должно быть повторяющейся связки `FightLink missing -> main.php -> main.php?r=...` в цикле;
  - должен появиться переход через submit формы завершения;
  - при капче должен открываться штатный captcha-flow без автосабмита пустого `code`.
