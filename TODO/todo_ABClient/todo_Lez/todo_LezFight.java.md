# Анализ и портирование: LezFight.cs → LezFight.java

## 1. План портирования LezFight.cs

**Назначение файла:** 
Ядро системы Авто-Боя. Парсит HTML страницы боя, анализирует доступные действия (удары, блоки, магию), генерирует оптимальные комбинации с учетом ограничений OD (очки действий) и маны, а также настроек группы противников. Возвращает HTML Frame с авто-submit формой для выполнения хода.

## 2. Функциональность в C# (LezFight.cs)

### 2.1 Основной алгоритм

1. **Парсинг HTML** — извлечение переменных:
   - `fight_ty` — тип боя, статус (в бою/ожидание)
   - `param_en` — параметры противника (имя, HP, MA, уровень)
   - `slots_en` — слоты противника (определяют тип)
   - `fight_pm` — боевые параметры: `magmax`, `odmax`, `hitval`
   - `stand_in`, `magic_in` — доступные действия игрока

2. **Определение группы противника** — выбор `LezBotsGroup` из профиля по Ida, уровню, типу (бот/человек/босс).

3. **Инициализация `_posod` и `_posma`** — массивы OD и маны для всех заклинаний. Индексы 0 и 1 заменяются на `hitval` и `hitval+20`.

4. **Генерация комбинаций**:
   - **Удары (Hits)**: 1, 2, 3, 4 удара по комбо слотам с учетом `_ehits` (разрешены ли удары в группе).
   - **Блоки (Blocks)**: по 1 блоку на комбо, с учетом `_eblocks`.
   - **Магия (Magics)**: 
     - Одиночные заклинания
     - **Комбинации из 2-х заклинаний** (если `magicCount > 1`)
     - **Комбинации из 3-х заклинаний** (если `magicCount > 2`)
     - Исключения: нельзя комбинировать `388` (Исцеление) с другими восстановительными, нельзя два блока в одной комбинации.

5. **Финальная сборка**: комбинации Hits + Blocks + Magics. Фильтрация по:
   - `OD <= _odmax`
   - `Mana <= _currentMa`
   - `IsValid()` — минимум 2 действия или магия+удар/блок

6. **Выбор лучшей комбинации**: 
   - Алгоритм хранит только комбинации с максимальным приоритетом `Z` (строка `_zScroll._zRestore._zMag._zBlock._zHit`).
   - Если несколько с одинаковым Z — добавляются все.
   - В конце выбирается случайная из лучших.

7. **Защитная проверка** (после выбора): если выбранная комбинация превышает OD, ищется альтернативная с OD <= _odmax среди `LezCombinations`. Если не найдена — `LezCombination = null`.

8. **Построение Frame**: HTML с формой `method=GET` (исправлено с POST для Android), параметры `inu`, `inb`, `ina`, `vcode` и авто-submit через `setTimeout`.

### 2.2 Критические отличия C# от первоначальной Java реализации

В C# присутствуют циклы генерации multi-magic комбинаций (2 и 3 заклинания), которые были опущены в первоначальной портировке на Java. Это ограничивало набор `_lezMagics` и могло привести к тому, что все комбинации с оптимальным Z имели завышенный OD, так как не были рассмотрены более эффективные комбинации с несколькими магическими заклинаниями.

## 3. Решение для портирования на Android

### 3.1 Проблема, выявленная 25.02.2026

**Симптомы:** 
- В логах множество `FILTERED OUT: OD=XXX/200`
- Авто-бой "висит" и не совершает удары
- Frame генерируется, но, возможно, не отправляется из-за отсутствия валидных комбинаций

**Анализ логов:**
```
Total valid combinations: 4
Selected combo: ... OD=170/200
```
Количество комбинаций мало (4), но OD в пределах. Однако если бы `odmax` был меньше, или настройки группы ограничивали действия, могли бы все комбинации иметь превышение OD.

**Вывод:** Неполная генерация `_lezMagics` (только одиночные заклинания) → ограниченный пул комбинаций → выше вероятность, что лучшие по Z будут превышать OD → пропуск хода.

### 3.2 Исправление 25.02.2026

Полностью портирована логика multi-magic генерации из C# (LezFight.cs строки 612-717) в `LezFight.java`:

- **Для `magicCount > 1`**: вложенные циклы по `flag1` и `flag2` с проверками:
  - `388` (Исцеление) не сочетается с `SpellsRestoreHp`
  - Два заклинания из `SpellsBlocks` запрещены

- **Для `magicCount > 2`**: тройные циклы по `flag1`, `flag2`, `flag3` с расширенными проверками на `388` и дублирование блоков.

Результат:
- `Total valid combinations: 11` (было 4)
- Комбинации включают multi-magic: `Magic[2:271,4:320]`
- OD выбранной комбинации: `180/200` (в пределах)

### 3.3 Почему Frame мог не отправляться

Frame генерируется корректно. Однако для успешного автоатаки требуется:
1. `mainPhpFight()` должен вернуть `fight.Frame` (логи `SAFE - returning fight.Frame`).
2. WebView должен перехватить GET-запрос (используется `method=GET`).
3. Сервер должен ответить новой страницей боя, и цикл повторится.

Если не было логов `SAFE - returning fight.Frame`, probable causes:
- `AppVars.Autoboi` не в `AutoboiOn`
- `LezDoAutoboi` выключен
- Сработали условия остановки (`DoStop`, `IsLowHp`, `IsLowMa`, `DoExit`)
