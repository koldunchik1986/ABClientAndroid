> Источник истины — `app2/src/main/java/ru/neverlands/anclient/utils/CryptoUtils.java`.

## ГЛАВНОЕ: фиксированной соли больше НЕТ

В новой схеме **нечего записывать как «новую соль»**.

| | Было (legacy 3DES) | Стало (ANC1) |
| --- | --- | --- |
| Соль | одна на всех, зашита в код: `"Ivan Medvedev"` | **случайные 16 байт на каждую операцию шифрования** |
| Откуда берётся | константа в исходниках | `SecureRandom.nextBytes(...)` |
| Где хранится | нигде (была в коде) | **внутри самой зашифрованной строки**, первые 16 байт конверта |
| Нужно ли её знать/хранить отдельно | — | **нет**, извлекается автоматически при расшифровке |

То есть у каждого зашифрованного значения **своя уникальная соль**. Даже если зашифровать один и тот же пароль дважды — соль (и результат) будут разными.

**Соль — не секрет и никогда им не была.** Её задача — не прятаться, а быть *уникальной*. Поэтому она открыто лежит рядом с шифротекстом, и это нормально (так работают все современные схемы: PBKDF2, bcrypt, scrypt, argon2).

**Единственный секрет — пароль шифрования, который вводит пользователь.** Он нигде не хранится в этом формате.

## Что вообще давала соль и что можно было сделать, получив её

### Зачем нужна соль

Соль подмешивается к паролю перед выработкой ключа:

```
ключ = PBKDF2(пароль + соль, число_итераций)
```

Она защищает не от расшифровки конкретного файла, а от **амортизации атаки**: чтобы злоумышленник не мог один раз посчитать таблицу «пароль → ключ» и применить её ко всем жертвам сразу.

### Что реально давало знание старой соли `"Ivan Medvedev"`

Сама по себе соль **не расшифровывает ничего**. Без пароля пользователя она бесполезна. Но она была статичной и общей для всех, и это открывало три возможности:

1. **Предвычисленная таблица (rainbow table) на всех сразу.**
   Соль одинаковая у каждого пользователя → злоумышленник считает таблицу «пароль → ключ» **один раз** и применяет её к профилям **любого числа людей**. С уникальной солью такую таблицу пришлось бы считать заново для каждого файла — атака перестаёт окупаться.

2. **Дешёвый перебор.**
   Соль в связке с `1000` итерациями PBKDF2 делала одну проверку пароля почти бесплатной. Имея украденный файл профиля, можно было перебирать словарь с огромной скоростью. Сейчас итераций `120 000` — это в **120 раз** дороже за каждую попытку.

3. **Утечка факта совпадения паролей (самое неприятное).**
   В старой схеме из пароля и соли детерминированно выводился **не только ключ, но и IV** (первые 16 байт — ключ, следующие 8 — IV). Отсюда следствие: одинаковый пароль + одинаковый открытый текст → **побайтово одинаковый шифротекст**.
   Это значит, что, просто сравнив два зашифрованных значения, можно было понять:
   * что два разных профиля защищены **одним и тем же** паролем шифрования;
   * что пароль **не менялся** между сохранениями.
   Никакой расшифровки для этого не требовалось. В ANC1 это невозможно: соль и IV случайные, поэтому два шифрования одного значения дают разный результат.

### Чего знание соли НЕ давало

* Не давало расшифровать профиль без пароля.
* Не давало «вычислить» пароль напрямую.
* Не было утечкой в привычном смысле: соль лежала в исходном коде (в том числе в ПК-версии на C#), то есть была публична с самого начала.

**Вывод:** проблема была не в том, что соль «могли узнать», а в том, что она была **одна на всех** и сочеталась со слабым шифром и малым числом итераций.

## Формат ANC1: спецификация

### Структура строки

```
"ANC1:" + Base64( salt[16] || iv[12] || ciphertext+tag )
```

| Поле | Размер | Описание |
| --- | --- | --- |
| префикс | 5 символов | `ANC1:` — маркер версии, по нему выбирается ветка расшифровки |
| `salt` | 16 байт | случайная соль, генерируется на каждое шифрование |
| `iv` | 12 байт | случайный nonce для GCM (рекомендованный размер) |
| `ciphertext+tag` | переменный | шифротекст + 16-байтный тег аутентичности |

Кодирование: `Base64` без переносов строк (`NO_WRAP`) — значение безопасно хранится в XML-атрибуте.

### Параметры

| Параметр | Значение |
| --- | --- |
| Шифр | `AES/GCM/NoPadding` |
| Длина ключа | 256 бит |
| Функция выработки ключа | `PBKDF2WithHmacSHA1` |
| Итераций | `120 000` |
| Длина соли | 16 байт (случайная, `SecureRandom`) |
| Длина IV/nonce | 12 байт (случайный, `SecureRandom`) |
| Длина тега GCM | 128 бит |
| Кодировка текста | UTF-8 |

### Почему PBKDF2 с SHA-1, а не SHA-256

`PBKDF2WithHmacSHA256` доступен только с **API 26**, а `minSdkVersion` проекта — **21**. Выбран один путь без ветвлений по версии Android; 120 000 итераций компенсируют выбор PRF. Использование SHA-1 внутри HMAC-PBKDF2 не подвержено известным атакам на коллизии SHA-1 — там важна стойкость HMAC, а не коллизионная стойкость хеша.

### Что даёт GCM дополнительно

Старая схема (`3DES/CBC`) не имела контроля целостности: подменённый шифротекст расшифровывался в мусор без всякого сигнала. GCM — аутентифицированное шифрование: любая модификация данных приводит к `AEADBadTagException`. Это проверено тестом (пункт «tampered ciphertext rejected»).

## Совместимость и миграция

* **С ПК-версией на C# — намеренно несовместимо.** Требование снято решением от 2026-07-26.
* **Старые локальные профили читаются.** `CryptoUtils.decrypt(...)` смотрит на префикс: если `ANC1:` нет — используется legacy-путь (3DES, статичная соль, 1000 итераций, windows-1251). Этот код оставлен **только для чтения**.
* **Ленивая миграция.** При первом успешном входе в старый зашифрованный профиль (`LoginActivity.migrateProfileEncryptionIfLegacy(...)`) он молча перешифровывается в ANC1 тем же ключом и сохраняется. В логах: `CRYPTO_MIGRATION: profile re-encrypted to ANC1`.
* Сбой миграции **не блокирует вход** — профиль просто остаётся в старом формате.

## Параметры legacy-схемы (только для чтения, справочно)

| Параметр | Значение |
| --- | --- |
| Шифр | `DESede/CBC/PKCS5Padding` (2-ключевой 3DES) |
| Соль | статичная 13 байт: `49 76 61 6E 20 4D 65 64 76 65 64 65 76` = `"Ivan Medvedev"` |
| Итераций | 1000 |
| Ключ / IV | выводились **вместе** из PBKDF2: первые 16 байт — ключ, следующие 8 — IV |
| Расширение ключа | 16 байт → 24 повтором первых 8 байт |
| Кодировка текста | windows-1251 |
| Контроль целостности | отсутствовал |

## Если понадобится менять параметры

Всё сосредоточено в константах `CryptoUtils`:

* `ANC1_ITERATION_COUNT` — компромисс «стойкость / задержка входа». Замер: одна операция ≈ **274 мс** на desktop JVM; на телефоне ориентировочно в 3-5 раз дольше. При входе в зашифрованный профиль выполняется 2 операции (основной + flash-пароль).
* При смене формата **обязательно** вводить новый префикс (`ANC2:` и т.д.) и оставлять чтение предыдущего — иначе сохранённые пароли станут нечитаемыми.
